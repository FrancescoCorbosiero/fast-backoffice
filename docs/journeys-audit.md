# Journeys: the dead ends found on the screens

Found by walking every admin screen as the owner does (November 2026), after the pass that made the contact and website pages lead somewhere (`docs/roadmap.md` › Journeys). Each line is a place where the obvious next step had no link, action or prefill; a ticked line has been fixed (November 2026). Impact and effort are the auditor's estimate; the fix is a proposal, to be checked against `docs/design.md` §4 before building. Tick a line when it ships.

## Contatti

- [x] **Qualsiasi form con 'Controparte' o 'Duplicato da unire' › '+ Crea contatto' inline** (high impact, small effort) — `ContactPicker::make('contact_id', [])` (MovementResource 'Controparte', ViewContact merge modal) creates the inline contact with `roles => []`; ContactValidator then throws 'Scegli almeno un ruolo.' The inline form has no roles field, so the owner registering a cash movement for a new counterpart cannot get past the modal and has no idea why. *Fix:* In `make()`, when `$roles === []` add `CheckboxList::make('roles')->label('Ruoli')->options(ContactRole::options())->default([ContactRole::Client->value])->required()` to `createOptionForm` and read it in `createOptionUsing`; when roles are given keep injecting them as today. (`app/Modules/Contacts/Filament/Components/ContactPicker.php`)
- [x] **Form fattura / preventivo / sito › campo Cliente › '+ Crea contatto' inline** (high impact, medium effort) — The inline form asks only kind, name, email and Partita IVA: no codice fiscale, no codice destinatario, no PEC. A consumer or a company created here from the invoice form has no SdI address, and the owner discovers it only when 'Emetti' fails, with no link from the picker back to the contact to fix it. Inline VAT typos also skip the in-place `vatRule` the full form has, so the validator's error does not land on the field. *Fix:* Share the field builders between ContactForm and the picker (e.g. `ContactForm::identityFields()`), add tax_code, sdi_code and pec (collapsed under 'Identità fiscale e SdI') with the same closure rules, and add `->suffixAction(Action::make('open')->icon(Heroicon::OutlinedArrowTopRightOnSquare)->url(fn ($state) => is_numeric($state) ? ContactResource::getUrl('view', ['record' => (int) $state]) : null)->openUrlInNewTab())` so the chosen contact is one click away. (`app/Modules/Contacts/Filament/Components/ContactPicker.php`)
- [x] **Form fattura / preventivo › campo Cliente › risultati della ricerca** (medium impact, small effort) — Search results read 'Nome · email' for every contact. When picking the customer of an invoice the owner cannot tell a contact that can be invoiced (P.IVA or codice fiscale, SdI routing) from one that cannot; the failure surfaces later at issue time. *Fix:* In `labels()` append a marker from ContactData: `· P.IVA 0123…` when `hasFiscalIdentity()`, otherwise `· senza identità fiscale`; optionally pass a `$needsFiscalIdentity` flag from Invoicing so such contacts are filtered out or shown last. (`app/Modules/Contacts/Filament/Components/ContactPicker.php`)
- [x] **Contatti › elenco** (medium impact, small effort) — A fresh install (and any filter that matches nothing) shows Filament's default empty state with no description and no CTA; 'Nuovo contatto' is only in the top-right header. The first journey of the whole app, 'add your first client', has no landing text. *Fix:* `->emptyStateHeading('Nessun contatto')->emptyStateDescription('Clienti, fornitori e collaboratori dello studio. Da un contatto nascono preventivi, fatture e siti.')->emptyStateIcon(Heroicon::OutlinedUsers)->emptyStateActions([CreateAction::make()->label('Crea il primo contatto')])`. (`app/Modules/Contacts/Filament/Resources/Contacts/Tables/ContactsTable.php`)
- [x] **Contatti › elenco** (medium impact, small effort) — 'My clients' and 'my suppliers' are two different lists in the owner's head, but here the role is buried in a SelectFilter dropdown; the owner opens Contatti and sees everyone mixed together each time. *Fix:* Add `getTabs()` on ListContacts: `Tab::make('Tutti')`, then one tab per ContactRole with `->modifyQueryUsing(fn (Builder $q) => $q->withRole($role))` and `->badge(fn () => Contact::query()->live()->withRole($role)->count())`; drop the role SelectFilter. (`app/Modules/Contacts/Filament/Resources/Contacts/Pages/ListContacts.php`)
- [x] **Contatto › pagina di dettaglio › Email, Telefono, PEC** (medium impact, small effort) — The most common next step on a contact page is to call or write to them. Email is copyable but not a mailto link; Telefono and PEC are plain text. The suppressed state is a text suffix rather than a visible badge. *Fix:* `TextEntry::make('email')->url(fn (Contact $r) => $r->email ? 'mailto:'.$r->email : null)->icon(Heroicon::OutlinedEnvelope)`, `phone` with `tel:` and `pec` with `mailto:`; replace the suffix with `->badge()`/`->color('danger')` state 'bloccata' or a separate `TextEntry::make('email_state')->badge()`. (`app/Modules/Contacts/Filament/Resources/Contacts/Schemas/ContactInfolist.php`)
- [x] **Contatto › pagina di dettaglio › Identità fiscale** (medium impact, small effort) — A client with no Partita IVA / codice fiscale shows '—' placeholders; nothing says 'you cannot issue an invoice to this contact yet' nor offers to complete it. The owner finds out from the invoice page later. *Fix:* Add a `Section::description()` or a `TextEntry::make('fiscal_state')->badge()` stating 'Identità fiscale mancante: non fatturabile' (warning) / 'Fatturabile via <recapito>' (success), with `->hintAction(Action::make('complete')->label('Completa')->url(ContactResource::getUrl('edit', ['record' => $record])))`. (`app/Modules/Contacts/Filament/Resources/Contacts/Schemas/ContactInfolist.php`)
- [x] **Contatto › Nuovo (form di creazione)** (medium impact, medium effort) — `FindContact::byEmail` and `SearchContacts` exist, but the form never tells the owner that a contact with the same email or a very similar name already exists; duplicates are only caught for VAT/tax code, and only as a blocking error. The merge tool then has to clean up what a hint on the form would have prevented. *Fix:* Make `email` `->live(onBlur: true)` with `->hint(fn (Get $get) => ($c = app(FindContact::class)->byEmail($get('email') ?? '')) ? 'Esiste già: '.$c->displayName : null)->hintAction(Action::make('open')->url(fn () => ContactResource::getUrl('view', ['record' => $c->id]))->openUrlInNewTab())`; same pattern on the VAT uniqueness error, which could carry a link to the other contact instead of a bare message. (`app/Modules/Contacts/Filament/Resources/Contacts/Schemas/ContactForm.php`)
- [x] **Contatti › elenco e pagina di dettaglio › badge Ruoli** (low impact, small effort) — `ContactRole::color()` exists (success/warning/info/gray) but neither the table nor ContactInfolist uses it: every role badge is the same grey, so clients and suppliers are indistinguishable at a glance in the list. *Fix:* On both roles columns/entries: `->state(fn (Contact $r) => $r->roleEnums())->formatStateUsing(fn (ContactRole $s) => $s->label())->color(fn (ContactRole $s) => $s->color())`. (`app/Modules/Contacts/Filament/Resources/Contacts/Tables/ContactsTable.php`)
- [x] **Contatto › Modifica** (low impact, small effort) — Edit is reached from the view page for one reason in most journeys: completing the fiscal identity before invoicing. The page opens on 'Chi' at the top, and saving sends the owner back to the contact page, not back to the invoice they came from. *Fix:* Honour a `?return=` query parameter (or `redirect()->getIntendedUrl()`) in `getRedirectUrl()` so Invoicing's 'Completa i dati del cliente' link can send the owner back to the draft; keep the view page as the default. (`app/Modules/Contacts/Filament/Resources/Contacts/Pages/EditContact.php`)

## Fatturazione

- [x] **Dashboard › widget Fatturazione (stat tiles)** (high impact, small effort) — All four stats ('Fatture da inviare a SdI', 'Da incassare', 'Scadute', 'Esiti SdI da gestire') are plain numbers with no url(), so the owner reads 'in ritardo di 3 giorni' or '2 scartate' and has to find the invoice by hand in the list. The invoice list also has no filter for overdue/outstanding, so even a link would have nowhere to land for 'Scadute' and 'Da incassare'. *Fix:* Add ->url(InvoiceResource::getUrl('index', ['tableFilters' => ['status' => ['value' => InvoiceStatus::Issued->value]]])) to the first stat, ->url(PecMessageResource::getUrl('index', ['tableFilters' => ['outcome' => ['value' => 'review']]])) (or the rejected filter) to the fourth, and add a Filter 'Incasso' (Da incassare / Scadute: outstanding() AND paid_cents < total_cents AND due_on < today) to InvoiceResource::table so the second and third stats can deep-link to it. (`app/Modules/Invoicing/Filament/Widgets/InvoicingOverviewWidget.php`)
- [x] **Fattura › pagina di dettaglio (fattura scaduta)** (high impact, small effort) — The journey 'overdue → remind the customer' has no step: when the header badge says 'Scaduta · residuo € X' the only actions offered are 'Registra incasso', 'Nota di credito' and downloads. The customer's email is shown only as a PEC line in the party block (if present), there is no way to contact them and no record that a reminder was sent. No reminder/sollecito action exists anywhere in the module. *Fix:* Add a header Action 'Sollecita' visible when paymentState() === PaymentState::Overdue, with ->url('mailto:'.$customerEmail.'?subject='.rawurlencode('Sollecito '.$data->title()).'&body=...residuo '.outstanding()->format()) ->openUrlInNewTab(), fed by FindContact for the email, plus optionally an audit entry; as a stopgap show the contact's email as a clickable entry in the header. (`app/Modules/Invoicing/Filament/Resources/Invoices/Pages/ViewInvoice.php`)
- [x] **Fattura fornitore › pagina di dettaglio** (high impact, medium effort) — The journey 'supplier invoice → payment movement' has no UI at all. The page shows 'Pagato € 0 su € X' and the list shows a permanent 'residuo' badge, but there is no 'Registra pagamento' action; the Cash movement form (MovementResource) has no allocation field either, so paid_cents can never become positive from the UI. RecordMovement accepts an allocation Reference and RebuildPaidAmounts already reconciles supplier_invoice references, so the backend is ready and only the entry point is missing. *Fix:* Add a header Action 'Registra pagamento' on ViewSupplierInvoice mirroring ViewInvoice's 'Registra incasso' (amount prefilled with outstanding(), paid_on, account_id Select from Accounts::options()) that calls a new Invoicing action (PaySupplierInvoice) wrapping Cash RecordMovement with Direction::Out, contact_id = supplier and allocation = the supplier invoice reference, then updates paid_cents; add a 'Pagamenti' Section listing the allocated movements like paymentsSection(). (`app/Modules/Invoicing/Filament/Resources/SupplierInvoices/Pages/ViewSupplierInvoice.php`)
- [x] **Fatture ricorrenti › elenco (nessuna pagina di dettaglio)** (high impact, medium effort) — The journey 'recurring invoice → the invoices it generated' is a dead end: the schedule has only list/create/edit pages, the generated invoice carries no recurring_invoice_id (IssueRecurringInvoice only writes the schedule name into notes), and nothing on the row leads to those invoices. The table also has no 'Cliente' column, so the owner cannot tell whose schedule a row is without opening the edit form. *Fix:* Add a TextColumn 'Cliente' (contact display name via FindContact, url to ContactResource view) and a record Action 'Fatture emesse' linking to InvoiceResource::getUrl('index', ['tableSearch' => $record->name]) or, better, add a nullable recurring_invoice_id on invoices set by IssueRecurringInvoice plus a ViewRecurringInvoice page with a 'Fatture generate' section (ContactInvoicesTable-style) and the schedule's next cycle, 'Emetti ora' and 'Sospendi' (DeactivateRecurringInvoice) as header actions. (`app/Modules/Invoicing/Filament/Resources/RecurringInvoices/RecurringInvoiceResource.php`)
- [x] **Fattura › pagina di dettaglio (fattura stornata)** (medium impact, small effort) — The credit note shows 'Storna → Fattura n. X' (related_invoice_id), but the original invoice never shows that a credit note exists for it: the owner opening an invoice that was fully credited still sees 'Da incassare · residuo € X' and a live 'Nota di credito' button, and can create a second storno by mistake. - [x] **Fattura / Richiesta di pagamento / Fattura fornitore › blocco Cliente e colonne Cliente** (medium impact, small effort) — The customer (or supplier) is rendered as a plain multi-line text block on every document page, and 'customer_name' / 'supplier_name' are plain text columns in the lists: there is no way to jump from a document to the contact's page (and from there to their other invoices, websites, quotes). - [x] **Fatture fornitori › elenco** (medium impact, small effort) — The list has no filters and no total: the owner wanting 'what do I still owe suppliers' (SupplierInvoices::payables() already exists and feeds the cash-flow projection) has to scan the 'Pagata' badge row by row. ## Preventivi e listino

The obvious next step is one click away but not offered. *Fix:* In the accept action's callback, redirect to InvoiceResource::getUrl('view', ['record' => $quote->invoice_id]) or PaymentRequestResource::getUrl('view', ...) according to the chosen AcceptanceOutcome (or at least attach a Notification action «Apri la bozza» with that URL); use the Resource getUrl helpers instead of the hardcoded url('/admin/invoices/…'). ViewLead already does this with «Contatto: apri»; the quote page does not. *Fix:* Add TextEntry::make('h_customer')->label('Cliente')->state($data->customerName)->url(ContactResource::getUrl('view', ['record' => $data->contactId])) to the header, and in QuoteResource::table() give the customer_name column ->url(fn (Quote $r) => ContactResource::getUrl('view', ['record' => $r->contact_id])). ## Cassa

- [x] **Cassa › Movimenti (list) › a movement logged from a recurring expense** (high impact, small effort) — Cash registers no AllocationPresenter for its own `recurring_expense:{id}:{date}` reference, so Allocations::label() falls back to toString(): the row's description sub-line reads literally 'recurring_expense:5:2026-03-01' and Allocations::url() returns null, so the owner cannot get from the payment to the schedule it belongs to. Also give MovementResource's description column ->icon(Heroicon::ArrowTopRightOnSquare) when allocated so the link is visible. (`app/Modules/Cash/Filament/Allocations.php`)
